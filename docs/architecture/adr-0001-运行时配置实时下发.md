# ADR-0001 运行时配置分层与实时下发（不引入 Apollo）

- 状态：已接受（老板拍板 2026-07-08）
- 日期：2026-07-08
- 相关代码：`src/configs/app_configs.py`、`src/services/system/runtime_config.py`、
  `src/services/system/app_settings.py`、`src/workers/scheduler_jobs.py`、`src/app.py`、
  `src/models/symbol_config.py`

## 1. 背景与问题

配置以 DB（`system_settings` 表）为真相源，前端设置页写入（Fernet 加密 + AuditLog）。
但每个进程把配置缓存进内存单例 `get_app_config()`（`@lru_cache`），且**没有跨进程的失效/下发机制**：

- **多 API worker**（`UVICORN_WORKER_NUM>1`）：前端 PUT 只命中一个 worker，`AppSettingsService._refresh()`
  只刷它自己；**其它 worker 仍是旧配置**。
- **scheduler 进程**：只在策略周期开头刷 DB（`refresh_runtime_settings_safe(source="pipeline_cycle")`，
  [scheduler_jobs.py:87](../../backend/src/workers/scheduler_jobs.py)，间隔 `STRATEGY_LOOP_INTERVAL_MINUTES` 默认 15min）；
  持仓监控(10s)/notifier 不刷 → 告警/风控用旧值，**最长滞后一个策略周期**。

目标：**服务启动后，前端改配置，运行中的进程按新配置调整（实时生效），且多 worker 一致。**

## 2. 配置分层（决策）

| 类别 | 内容 | 存储 | 改了怎么生效 |
|------|------|------|--------------|
| **A 基础设施/启动骨架** | PG/Redis 连接、连接池、`APP_AUTH_SECRET_KEY`/`APP_CONFIG_MASTER_KEY`、worker、CORS、**扫描间隔**（`STRATEGY_LOOP_INTERVAL_MINUTES`/`POSITION_MONITOR_INTERVAL_SECONDS`/`STRATEGY_SCORING_INTERVAL_HOURS`）、事件总线/队列名 | **env** | 重启/重部署 |
| **B 业务运行参数** | 币安 Key/网络、LLM(Key/BaseURL/Model/温度)、风控 4 阈值、通知(开关/级别/Telegram) | **DB `system_settings`** | **实时** |
| **C1 交易标的** | 币种/timeframe/启用/优先级（`symbol_configs` 表已存在 + `/api/admin/symbols` UI） | **DB `symbol_configs`** | **实时** |

**显式暂缓（本 ADR 不做）**：
- C2 每标的仓位上限 `max_position_size_pct` 接入 guard（老板未定）。
- 指标参数化（EMA/RSI/MACD/ATR/布林 周期）——耦合 DB 列名 + prompt + regime 语义，风险高，单独立项再议。
- 扫描间隔运行时可调（APScheduler `reschedule_job` 技术可行但价值低，归 A/重启）。

## 3. 决策

**不引入 Apollo 等独立配置中心。** DB 已是配置真相源（含加密/审计/UI），Redis Pub/Sub + Streams 事件总线已在运行；
配置中心唯一能补的"变更推送"用现有 Redis 即可实现。为单机 2-3 进程、单人运维引入 Apollo（重型 Java 集群 + 自带 MySQL）
运维不成比例、重复造存储、削弱密钥加密，规模也错配。

**采用「DB 真相源 + 进程内快照缓存 + 变更失效重载」范式**，分两步增量实现：

- **P1 短周期兜底刷新**：各进程按 ~10s 周期调 `refresh_runtime_settings_safe`（全快照重载 ≈1-5ms），
  把延迟从 ≤15min 压到 ~10s，先止血。
- **P2 Redis 广播**：写配置提交后发 `config.changed` 到 Redis，各进程订阅即重载 → 毫秒级 + 多 worker 一致。
  P1 的周期刷新保留为**兜底**（Pub/Sub 尽力投递，漏消息最迟一个周期自愈）。

**不采用「每次用配置去 Redis/DB 查」**：配置在热路径高频读，每字段一次往返会拖慢核心链路、造成一次操作内的撕裂读、
且密钥要么明文进 Redis 要么每读一次解密。快照缓存 + 变更失效才是标准解，且重载便宜。

## 4. 备选方案与否决理由

| 方案 | 否决理由 |
|------|----------|
| Apollo/Nacos 配置中心 | 运维重、重复造存储、削弱密钥加密、规模错配（详见 §3） |
| 每次用配置查 Redis | 热路径多往返、撕裂读、密钥明文/反复解密 |
| 每次查 DB | 同上且更慢 |
| 只保留周期刷新、缩到极短 | 轮询浪费、仍非真实时；P1 已够兜底，P2 才是终态 |

## 5. 影响

**正向**：真实时下发；多 worker/scheduler 配置一致；零新依赖、零新运维；复用现有 `apply_runtime_settings_refresh`。
**负向/代价**：P1 每进程 ~10s 一次小查询（可加 Redis 版本号跳过无变更重载）；P2 需在所有写配置路径收口发布（有漏发风险，靠 P1 兜底 + 集中发布点缓解）。

## 6. 分阶段实施计划

### 阶段 P1：短周期兜底刷新（止血）
- **目标**：scheduler + API 各进程 ≤10s 内感知 DB 配置变更。
- **改动**：
  - scheduler：注册一个 ~10s 的 APScheduler job `config_refresh`，调 `refresh_runtime_settings_safe(source="periodic")`；
    或并入持仓监控 job 开头。
  - API：lifespan 起一个 asyncio 后台循环，每 ~10s 调一次刷新（每 worker 各自跑）。
  - 保留现有 startup + pipeline_cycle 刷新。
- **测试**：单测刷新后单例字段更新；集成：PUT 改设置 → ≤10s 内 scheduler 单例反映。
- **成功标准**：改风控阈值/通知级别，无需重启，~10s 内在 scheduler 生效。

### 阶段 P2：Redis 广播（真实时 + 多 worker 一致）
- **目标**：写配置后毫秒级下发到所有进程。
- **改动**：
  - 新增 `publish_config_changed(keys)` 发到 Redis 频道 `alphapilot:config`。
  - **发布点收口**：`AppSettingsService.put_*`、runtime_config PUT、`pilot_agent` apply 提交后统一发布（集中一处，别散落）。
  - 订阅：API 扩展现有 `redis_subscriber`（[app.py](../../backend/src/app.py)）加 config 频道 → 调刷新；
    scheduler 在 event_shuttle 常驻循环里加 config 频道订阅 → 调刷新。
  - 保留 P1 周期刷新做兜底；可选：Redis 存 `config_version`，兜底刷新先比对版本跳过无谓重载。
- **测试**：mock/fakeredis 验证 publish→subscriber 触发刷新；集成：PUT → 各进程 ~即时反映；
  杀订阅者→改配置→重启→兜底自愈。
- **成功标准**：前端改配置，API 各 worker + scheduler 近乎瞬时一致。

### 阶段 C1：交易标的接 `symbol_configs`
- **目标**：决策链交易 `symbol_configs`(enabled) 里的币，而非 env `PIPELINE_SYMBOLS`。
- **改动**：
  - [scheduler_jobs.py:100](../../backend/src/workers/scheduler_jobs.py)：`_parse_csv(settings.PIPELINE_SYMBOLS)` →
    `symbol_config_crud.find_enabled(db)`，取 symbol + 每标的 timeframe（缺省回退 env/默认）。
  - env `PIPELINE_SYMBOLS`/`PIPELINE_TIMEFRAMES` 降级为 `ensure_default_symbol_configs` 的 seed 兜底。
  - 决策链每周期开头读表，天然"次周期生效"；叠加 P1/P2 刷新近乎实时。
- **测试**：启/禁用某 symbol → 下一周期纳入/剔除；禁用的不下单。
- **成功标准**：后台 `/api/admin/symbols` 开关币种，无需重启即改变实际交易范围。

## 7. 边界与风险

1. **Pub/Sub 尽力投递**（订阅者重启会漏）→ P1 周期刷新兜底自愈；要更强用 Redis Streams(`RedisStreamsBus`)。
2. **发布点必须全覆盖**（三条写路径）→ 集中一个 `publish_config_changed`，别在各处散发。
3. **整快照重载**（非增量 diff）→ 以 DB 为准 last-reload-wins，避开并发顺序竞争。
4. **A 类不热重载**（PG 连接池/主密钥/扫描间隔）→ 改了重启，安全且够用。
5. **密钥保持 DB 内 Fernet 加密**，各进程解密进单例，机制不变。
6. **交易安全**：pipeline 周期开头读配置，风控收紧最迟 ~10s(P1)/瞬时(P2) 生效；不会因热更导致一次决策内配置撕裂。
