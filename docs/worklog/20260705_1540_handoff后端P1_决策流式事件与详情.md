设计侧交付包 `AlphaPilot Design System/handoff/` 落地开工。老板指令：本会话只做服务端，前端由并行会话实现；核心规格是 `handoff/03_API_差距与新增接口.md`，按 `04_实现路线图.md` 分期推进（P0 纯前端，后端从 P1 起步）。Python 版本按仓库规范固定 3.12（交接 prompt 中的 3.11 作废）。

实现计划：`docs/superpowers/plans/2026-07-03-handoff-backend-p1-decision-streaming.md`。

## 做了什么

对应 handoff 3.3（决策流式可视化）：

1. **事件契约**（`src/services/events/contracts.py`）：新增 `DecisionProgress`（stage: snapshot|reasoning|guard|verdict|execute × status: start|done|fail）与 `DecisionComplete`（完整决策收尾摘要），注册进 `EVENT_TYPE_REGISTRY`。
2. **进度发射器**（`src/services/events/progress.py`）：`DecisionProgressEmitter` 用独立 session 写 event_outbox 并立即 commit——管道单 symbol 事务在末尾才提交，若进度事件走同一 session，LLM 思考期间前端看不到任何推进。内部异常一律吞掉只记 warning（进度可视化绝不能影响交易主链路）；`fail_current()` 在管道异常时对最后 start 的阶段补发 fail。
3. **管道埋点**（`src/workers/strategy_pipeline.py`）：五阶段 start/done 埋点 + 指标不足时 snapshot fail + 末尾发 `decision.complete`（与业务写同事务走 outbox 保原子性）。`run_strategy_pipeline_once` 新增可选参数 `progress_emitter`，不传完全兼容旧行为。scheduler 接线在 `src/workers/scheduler_jobs.py`。
4. **守卫审计关联决策**：`risk_events` 表加 `decision_id` 可空列 + 索引（alembic 迁移 `20260705_153211_6e79e5d8e1f6`，由 `alembic revision` 命令生成），`ExecutionGuard._record` 落 decision_id，详情端点可反查守卫结果。
5. **决策详情**：`DecisionDetailService`（`src/services/strategy/decision_detail.py`）聚合决策主行 + features（因子快照 factors_json + prompt_input）+ review + 守卫审计行 + 关联 orders/positions；4 个 crud 补 `find_by_decision_id`；新端点 `GET /api/decisions/{id}`（登录可见，跨 trading_mode 不可见）。

## 为什么

- 前端 P1 的 StreamingDecision 组件靠 `decision.progress` 逐段点亮、`decision.complete` 展开完整决策卡（handoff 02 §P2/P4）；决策详情页需要 features 快照、守卫结果、reasoning 全文、关联订单（handoff 03 §3.3）。
- 守卫"逐项结果"本期以 GUARD_* 审计行呈现（短路式守卫单次调用只产生一条命中记录）；真正 per-check 明细将在 P2 手动下单预检接口（`POST /api/orders/precheck`）随守卫重构一并补齐。
